Research report · 17 October 2026

What the emails release asset proves—and does not

GitHub lists an original emails-source.zip asset in release v2.11.37. The tagged emails/SKILL.md source displays 2.1.4. We could not read the ZIP bytes or attached manifest, so no path inside the selected ZIP is confirmed present or missing.

Decision unchanged

For one approved, non-personal post-signup welcome brief, start with an owner-maintained template and reviewed prompt. The five-email Markdown format is our proposed draft hypothesis, not a source-required length or configured flow. A named owner checks proof, terms and exact CTA. Recipient-policy and ESP owners separately decide eligibility, consent, suppression, overlap, timing and every import, setup, test, schedule or send. This source check authorizes none of those actions.

Three evidence layers

The published asset

GitHub release metadata reports publication on 15 October 2026 at 18:35:22 UTC, target commit 365b412152b9542499ca1439426f7fc3cc92bb65, and an emails-source.zip asset (ID 644792940; created 18:35:29 UTC; 14,583 bytes). GitHub reports SHA-256 b605c474886414be0232034938e53effdf54112d690727f462fbb29304c0beaf. This is a reported metadata value, not a checksum computed from downloaded bytes.

The access boundary

The direct ZIP and attached manifest URLs returned a web-broker cache miss. A local HTTPS request failed at DNS resolution before an HTTP response. The release connector supplied metadata, not either body. We did not open a ZIP central directory, compute a hash, rebuild an archive, inspect manifest fields, or install anything. Inaccessibility does not show that the assets are absent.

The release metadata marks immutable: false. The tagged packaging document says reruns may replace named assets at the same tag. The reported digest is therefore a dated observation, not a permanent pin.

Named paths are not confirmed ZIP entries

The tagged source file has Git blob SHA-1 e660baf4adf7430ff90bfbdeaf9a9ad101a2d2ed and displays version 2.1.4. It names three same-folder references, a Copywriting AI-tells cross-reference, and separate implementation URLs. Git blob SHA-1 IDs are not the release-reported archive SHA-256 or file-byte checksums.

What would close the gap?

  1. Obtain the original bytesUse a readable download of the selected source ZIP and attached manifest, not a rebuilt substitute.
  2. Check the dated digestCompute SHA-256 on the bytes and compare with the release metadata observed here.
  3. Read entries and fieldsInspect central-directory names and manifest fields read-only; record each present or missing path separately.
  4. Keep decisions separateArchive content would not by itself verify a CLI-selected payload, host resolution, permission, quality, deliverability or recipient-policy approval.
Still unknown: exact ZIP entries and packaged hashes, manifest comparisons, actual CLI-selected files, cross-skill or URL resolution, current mutable selected-file state, host permissions, safety, quality, deliverability and outcomes. No account, list, provider, brief, draft, install or send was used. No compatibility, legal, privacy, security, AI-detection or marketing-result conclusion follows.
